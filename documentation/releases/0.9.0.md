# Homi 0.9.0+11 — safety, arrival check-ins and clearer people identity

## Scope

0.9.0 adds a safety/check-in layer to the approved 0.8 product without changing Homi's primary navigation or established brand foundation.

This source pass includes:

- South African emergency call shortcuts under People → Safety & check-ins;
- explicit Home and Work arrival check-ins for selected trusted Homi connections;
- clearer Household versus Friends & trusted people grouping on the People destination;
- profile photos in household Task assignment controls;
- useful operational notifications enabled by default for fresh installs, subject to Android's system notification permission.

## Emergency calls

The Safety & check-ins screen exposes three South African emergency shortcuts:

- Emergency/mobile: `112`;
- Police emergency: `10111`;
- Ambulance emergency: `10177`.

Homi uses the device phone application through a `tel:` URI. It does not silently place calls, request the Android direct-call permission, dispatch responders or automatically transmit the user's location to an emergency service.

The user-facing screen states this boundary explicitly.

## Arrival check-ins

Arrival check-ins are explicit and user-configured:

1. the user signs in;
2. while physically at Home or Work, they save that current location;
3. they choose an arrival radius (150 m, 250 m or 500 m in the current UI);
4. they choose which accepted trusted Homi connections should receive that place's check-in;
5. they deliberately turn Arrival check-ins on.

Saved Home/Work coordinates remain local to the device in user-scoped preferences. The callable backend receives only the place label (`home` or `work`) and selected trusted-recipient UIDs. Coordinates are not included in the arrival notification payload or callable request.

Check-ins reuse Homi's existing visible Android foreground live-location service. Background operation therefore requires Android location access set to **Allow all the time** and retains the visible Homi location notification. Force-stopping the app can interrupt this behaviour until Homi is opened again; the feature must not be represented as an emergency monitoring guarantee.

### Arrival detection

Homi does not announce an arrival merely because the app opens while the user is already inside a saved zone.

The local detector:

- primes the initial inside/outside state without sending;
- sends only on an outside → inside transition;
- requires moving more than 100 m beyond the configured radius before considering the user outside again, reducing GPS edge flapping;
- keeps a one-hour local cooldown per saved place;
- creates no route or movement-history record.

When check-ins are turned off, Homi stops the continuous foreground location stream if it can confirm that no explicit per-person live-location shares remain active. If it cannot safely prove there are no active viewers, it leaves the existing live-location stream untouched rather than silently breaking another sharing choice.

## Arrival notification backend

New callable Function: `sendArrivalCheckIn` in `africa-south1`.

The callable:

- requires Firebase Authentication;
- requires verified email for password-provider accounts;
- enforces Firebase App Check;
- accepts only `home` or `work`;
- accepts 1–10 unique non-self recipients;
- verifies every recipient is an accepted trusted connection;
- applies fixed-window sender rate limits (20/hour and 60/day);
- reads at most 12 push-enabled device records per recipient;
- respects each recipient device's People-notification preference;
- includes no coordinate data in the push payload;
- uses Homi's existing People notification channel and route.

The existing batched backend deployment helper automatically discovers this new export from `functions/entrypoint.js`.

## People destination

The primary People destination is now a lightweight People hub rather than immediately opening the dense live-location/connection manager.

Accepted people are separated into:

- **Household** — accepted connections explicitly marked Household;
- **Friends & trusted people** — accepted non-Household connections.

Both sections use the existing stored connection profile image where available. Pending connection requests remain surfaced. The approved existing People map/location/relationship implementation is preserved behind **Manage connections & live location** rather than removed or rewritten.

Safety & check-ins is available from the People hub. Emergency call shortcuts do not require a Homi account; arrival check-ins do.

## Task assignment identity

Task assignment continues to use `HouseholdPeopleService`, so non-Household connections are not exposed as household assignees.

The assignee picker now shows:

- the current user's profile image where available;
- each Household person's existing connection profile image;
- a safe initials/person fallback when no image is available;
- the existing Anyone at home group option.

No Task authorization rule was loosened for this visual change.

## Notification defaults

Fresh-install Homi notification preferences now default to:

- master operational notifications: ON;
- Household attention: ON;
- Tasks & routines: ON;
- People: ON;
- Service & security: ON;
- Homi Updates/product announcements: OFF.

The distinction is deliberate: useful operational notifications default on, while optional product/update announcements remain opt-in.

Android 13+ still controls the actual runtime notification permission. Homi asks for that system permission once on a fresh install. If the user denies or dismisses it, Homi does not repeatedly interrupt them; they can enable notifications later from Homi & account → Notifications or Android Settings.

Existing saved Homi notification preferences are preserved, including an existing user's explicit master OFF choice.
