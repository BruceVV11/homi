## Purpose

0.12 is the first real shared-Household data-plane pass. It builds on the canonical Household identity introduced in 0.11 without replacing the approved local-first app or silently uploading data that belongs to a different Household.

It also closes the People issues found during Bruce's 0.11/0.12 device review:

1. trusted People were appearing after location/identity startup work instead of subscribing immediately;
2. Household connection scope could be represented as a user-editable People preference;
3. Bruce's reusable Homi code was not reliably accessible in the populated Connections state;
4. an established code was unnecessarily dependent on a fresh protected callable, so an App Check/Auth proof problem could hide a code already stored on the account;
5. Household **Add person** used an easy-to-miss inline message when there was nobody else eligible to invite;
6. the reusable Homi code was visually duplicated in a persistent Connections card even though **My code** already provided an intentional on-demand access point.

## People and connection UX

### Immediate People subscription

`PeoplePage` now starts its accepted-connection and preference subscriptions independently of cached GPS loading, passive location refresh and continuous-location resume. Location startup continues in parallel.

This removes the structural wait that caused the Connections area to remain empty for roughly the first second or two even when Firestore could already supply the People list.

### Reusable Homi code remains available

The populated Connections header exposes **My code** beside **Connect**. The code is intentionally not repeated in a persistent card below the header. Tapping **My code** opens the dedicated Homi-code sheet, where the reusable six-character code can be viewed and copied.

For an already-provisioned account, `TrustedPeopleService.ensureIdentity()` reads the signed-in user's self-readable `users/{uid}` profile first and reuses its valid `homiCode`. The existing `ensureHomiIdentity` callable remains the provisioning/repair fallback for a new or incomplete profile. This avoids requiring a fresh protected callable merely to display an established reusable code.

If code loading genuinely fails when **My code** is requested, Homi now presents the failure in the branded information-sheet pattern instead of leaving the user with a silent tap or a persistent error card in the Connections page.

Bruce's 2026-09-12 S25 Ultra review confirmed that the established code `WG4JTZ` loaded correctly from the account profile and that the revised Connections controls were working before the final cosmetic removal of the persistent code card. The final cosmetic source change therefore still requires the exact-head analyzer/test gate and one focused device glance before merge.

### Household is no longer a manually selectable People scope

A relationship label such as Partner, Friend, Mother or Roommate remains user-editable. **Household** versus **Friend · location only** is read-only in that edit sheet.

The displayed Household state is derived from the canonical `households/{householdId}.memberUids` membership rather than from the old `peoplePreferences.scope` value. The sheet explains:

- create a Shared Household first if none exists;
- invite an accepted connection from **Homi & account -> Shared Household**;
- the invitee must accept before Household access exists;
- existing Household membership is managed from Shared Household rather than by changing a People label.

The protected `setTrustedPersonPreference` callable keeps its deployed name for client compatibility, but its server implementation ignores caller-supplied scope and derives `household` only when both accounts belong to the same canonical Household. Otherwise it stores `friend`.

`HouseholdPeopleService`, used by shared task assignment, also derives its people list from canonical Household membership rather than the preference scope.

### Household Add person empty state

If the Household owner taps **Add person** when every accepted trusted connection is already a member or already has a pending invitation, Homi now uses a branded informational bottom sheet instead of injecting an inline error card into the page after the tap.

The sheet distinguishes:

- a genuinely full four-seat Household;
- existing eligible connections already being members/pending; and
- needing to connect with another person in People first.

Connection-load failures on this action use the same visible custom information sheet and do not mutate the Household.

## Shared Household data plane

### Canonical path

Shared Household records are stored under the exact canonical Household:

`households/{householdId}/data/{domain--itemId}`

The outer envelope contains:

- `domain`
- `itemId`
- `payload`
- `schemaVersion`
- `updatedByUid`
- `updatedAt`

0.12 supports these domains:

- `routine`
- `supply`
- `homeThing`
- `homeEvent`
- `utilityReading`

The document ID is deterministic and must equal `domain--itemId`.

### Local-first write model

The existing `HomiAppController` remains the immediate device authority. A user action first updates and persists SharedPreferences exactly as the app did before 0.12. A Household mutation sink then mirrors eligible shared records to Firestore.

This means a temporary cloud failure does not make Home, Routines or Supplies unusable. Firestore's normal local cache/write queue remains available for Household writes while connectivity changes.

Applying a Firestore snapshot uses dedicated controller methods that persist the cloud result locally without echoing the same change back to Firestore.

Explicit Homi local-only mode suppresses this synchronizer even if Firebase still has a cached authenticated user. Re-entering the account/cloud flow recreates the shell after `localOnly` is disabled, allowing sync to start deliberately.

### First-sync migration rule

Existing device data is never blindly uploaded on every Household join.

For the **first owner of a brand-new Household whose authoritative server data collection is empty**, 0.12 imports the device's existing:

- Routines;
- Supplies;
- Home Things;
- maintenance/repair events; and
- utility readings.

The migration waits for a non-cache Firestore snapshot before deciding that the Household is empty. A cached empty snapshot is not accepted as proof that a server Household contains no records.

For a member joining an existing Household, or a device that later changes Household, pre-existing local IDs that are not already known Household records are classified as **private legacy data**. They remain on that device and are not silently uploaded. New records created after Household classification are shared normally.

A later explicit merge/import UI can promote those private legacy records; 0.12 deliberately does not guess which Household old data belongs to.

### Conflict rule

Synchronization is record-based. Distinct item IDs merge naturally. For two devices changing the same item, the last Firestore write acknowledged by the server becomes the shared value and is subsequently persisted to each listening device.

No local dataset is erased simply because a user leaves a Household. Membership removal stops cloud access and cloud mutation, while the device retains the local copy it already had.

## Tasks

Personal **Me** tasks remain private/local as before.

Shared one-off Tasks continue to use the existing `sharedTasks` collection and client UI, but the three existing callable names are overridden by a canonical implementation:

- `createSharedTask`
- `toggleSharedTask`
- `removeSharedTask`

New shared Tasks derive their `memberUids` and `householdId` from the creator's canonical Household. A caller cannot manufacture Household task access by setting a People preference to Household. A task cannot be assigned to a user who has not joined that canonical Household.

0.12 also adds `onHouseholdTaskMembershipChanged`. When a canonical Household member list changes, it updates **new 0.12 Tasks carrying that Household ID** to the current member list. A removed assignee is reset to Unassigned; removed completion attribution is reduced to a former-member label rather than retaining a stale UID.

Pre-0.12 Tasks are handled by the governed migration described in `documentation/releases/0.12.0-shared-task-migration.md`. Safe legacy Tasks receive a canonical Household ID without widening their historical recipient audience. Unsafe/unmappable legacy Tasks fail closed rather than being deleted merely to make the migration pass.

The callable names remain unchanged so current clients do not need a protocol migration.

## Firestore boundary

`households/{householdId}/data/{recordId}` requires both:

1. the caller's `householdMemberships/{uid}` pointer to reference that Household; and
2. the Household's server-owned `memberUids` list to still contain the caller.

For creates/updates the rules also require the fixed 0.12 envelope, an allowed domain, deterministic `recordId`, matching payload/item identity, `schemaVersion == 1`, the authenticated `updatedByUid`, and `updatedAt == request.time`.

A membership pointer alone cannot forge access, and a stale Household member list alone cannot keep access after the membership pointer is removed.

## Household deletion cleanup

Firestore does not automatically delete document subcollections when a parent Household document is deleted. 0.12 therefore adds `onHomiHouseholdDeletedDataCleanup`.

After a canonical Household document is removed, the trigger deletes its nested shared `data` and canonical `sharedTasks` subcollections in bounded batches. This prevents unreachable Household data from becoming orphaned cloud storage.

Together with the new Household-task membership trigger, the governed Functions export surface increases from 35 to **37**. The preference/task implementation modules override existing callable names and therefore do not add additional public export names. The deployment helper's exact export-count guard and source-completeness checks are updated accordingly.

## 2026-09-26 backend release qualification findings

The first governed Cloud Shell release attempt stopped **before any Firebase production mutation**. It proved Node 22, project identity, the dedicated runtime identity, Functions dependency install/lint, shared-task policy **5/5**, exactly **37** Function exports, and the presence of all **23** Firestore security tests. The Firestore gate then failed during dependency installation because the security harness had accidentally combined `@firebase/rules-unit-testing@4.0.1` with Firebase `12.3.0`.

A focused dependency correction restored the previously compatible Firebase 12-generation pair. The next focused emulator run progressed through dependency installation and executed all 23 tests: **21 passed and 2 failed**. Both failures were the same canonical shared-Task list query. Individual canonical task `get` access worked, but list authorization could not be proven because the rules derived the Household document lookup path from `resource.data.householdId` during a query.

A first rule-only correction then anchored external Household lookups to the authenticated user's server-owned `householdMemberships/{uid}` document. The exact corrected candidate still produced the same **21/23** result: both collection-list cases remained denied. That repeated signature demonstrated the root Firestore limitation rather than another dependency problem: a root collection query cannot safely prove the required per-user external Household value against every potential result merely because the client supplies a matching `householdId` filter.

The durable correction moves canonical shared Tasks to `households/{householdId}/sharedTasks/{taskId}`. Household identity is therefore part of the request path, matching the same path-scoped authorization pattern already proven by the Household data-plane tests. The client queries only that exact subcollection plus `memberUids array-contains uid`. The root `sharedTasks` collection becomes a migration-only fail-closed source. Safely mappable root Tasks are copied into the exact Household subcollection and deleted from the root in one batch; migrated version-0 audiences may shrink on member removal but never widen on later joins.

The first full qualification of the nested-path candidate proved the broader correction but still finished **21/23**. Direct nested Task `get` operations succeeded and every non-Task-list boundary passed; only the two nested collection queries were denied at the Task `list` rule. Source comparison against the already-green canonical Household collection rule exposed the remaining difference: the Task rule repeated `resource.data.memberUids is list` during `list` evaluation, while the proven Household collection rule intentionally omits its redundant type assertion and relies on the client `array-contains` constraint. The Task rule now follows that same split contract: direct `get` retains the explicit list type check, while `list` requires canonical Household membership plus `memberUids.hasAny([auth.uid])`; the `array-contains` query itself excludes non-array values. The existing 23-test suite is strengthened without increasing its count so a malformed stored audience still fails closed on direct read.

The two existing root notification triggers are replaced by renamed nested-path triggers before the old names are removed, following Firebase's governed trigger-migration pattern. The canonical callable names stay stable, and the final Function export count remains **37** because the two retired trigger exports are replaced one-for-one.

No migration, Firestore rule/index deployment, or Function deployment has occurred from any failed qualification run.
