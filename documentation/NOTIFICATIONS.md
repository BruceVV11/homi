# Homi Notifications

Date: 2026-09-10
Source version: `0.8.0+8`

## Product principle

Homi notifications exist to reduce uncertainty, not create another stream of noise.

The notification system separates:

1. household attention generated from data on the current device;
2. shared household / trusted-person events generated by Homi's cloud backend;
3. developer product, service and security notices;
4. the always-visible Android foreground-service notification used while live location sharing is active.

The foreground live-location notification is operational Android disclosure and is not controlled by the optional reminder categories below.

## User permission and preferences

Homi does not request normal notification permission at first launch. The user can enable notifications from:

**Profile avatar → Homi & account → Notifications**

The device-level Homi settings are:

- Household attention
- Tasks & routines
- People
- Homi updates
- Service & security

The master switch applies only to this installation. Category choices are stored locally and, for a signed-in device, mirrored with its FCM device registration so the backend can avoid direct messages the installation has disabled.

Developer broadcast categories use FCM topic subscriptions so a local-only installation can receive Homi product/service notices without creating an account. Topic subscriptions are updated when the user changes the relevant category.

## Local household notifications

Local household reminders use `flutter_local_notifications` and are rebuilt from the local Homi state whenever the user changes Tasks, Routines, Supplies or Home records.

Current behaviour:

| Event | Timing | Category | Destination |
| --- | --- | --- | --- |
| One-off Task with due time | saved due date/time | Tasks & routines | Tasks |
| Recurring Routine | next due date/time | Tasks & routines | Routines |
| Supply expiry warning | 3 days before at 09:00 when schedulable | Household attention | Supplies |
| Supply expiry date | expiry date at 09:00 | Household attention | Supplies |
| Home service warning | 7 days before at 09:00 when schedulable | Household attention | Home |
| Home service due | service date at 09:00 | Household attention | Home |
| Newly out-of-stock / Need to buy Supply | once when entering the critical state | Household attention | Supplies |

Scheduled local reminders use inexact Android scheduling rather than exact alarms. Homi therefore does not request exact-alarm permission. Android may defer an inexact reminder while the device is conserving power.

Homi stores notification IDs for the schedules it owns, cancels/rebuilds only those IDs, and does not cancel unrelated Android notifications.

## Noise control

Current anti-nag rules:

- notifications are user enabled rather than automatically opted in;
- category-level switches are available;
- expiry/maintenance housekeeping reminders use 09:00 rather than overnight delivery;
- critical Supply changes are de-duplicated while the item remains in that state;
- only the nearest 60 local schedules are retained after sorting chronologically;
- broad developer notices use only product, service or security categories and cannot masquerade as a personal People/Task notification;
- a People heart has a server-side one-minute sender→recipient cooldown;
- no long-term location history or coordinates are placed in notification text.

## FCM device registration

When notifications are enabled and a user is signed in, Homi stores the current FCM registration token under:

`users/{uid}/devices/{deviceId}`

The document includes:

- push token
- platform
- notifications enabled flag
- Household attention preference
- Tasks & routines preference
- People preference
- Homi updates preference
- Service & security preference
- updated timestamp

The device ID is a random app-installation identifier stored in Homi local preferences. It is not a hardware serial or advertising identifier.

Signing out removes the push token from that signed-in user/device record before ending the Firebase Auth session. Account deletion also removes current device registration and the existing account-deletion pipeline deletes the user's device subcollection.

Invalid/unregistered FCM tokens discovered during direct server delivery are removed and disabled automatically.

## Trusted-person notifications

Cloud Functions produce direct, preference-aware notifications for authenticated relationship/collaboration events.

### Connection request

Recipient receives a Homi People notification when another user sends a connection request.

### Connection accepted

The original sender receives a People notification when the invited user accepts.

### Hearts

The full People map exposes a small heart action for a selected trusted person. It is deliberately simple:

- only an authenticated user may send;
- the recipient must be an accepted trusted connection;
- sending does not change location sharing, household scope or any relationship permission;
- the server applies a one-minute cooldown for each sender→recipient pair;
- the recipient sees **“{name} is thinking about you!”**;
- tapping the notification opens People.

### Shared Tasks

When a shared Task is created, the selected assignee is notified, or the household-visible members are notified when the Task is for Anyone at home.

When somebody other than the Task creator completes it, the creator receives a completion notification.

Lock-screen notification bodies intentionally avoid reproducing the Task title. The user opens the authenticated Homi Tasks surface to read household content.

## Developer notification control

Developer notification access is not a normal user role and cannot be self-granted by the app.

An authorised developer account has a `developerAdmins/{uid}` record provisioned outside the client. The Account centre then shows **Developer notifications**.

The composer supports:

- title (maximum 80 characters)
- message (maximum 280 characters)
- type: Homi update / Service or maintenance / Security
- audience: current developer account test / all enabled Homi installations
- deep-link destination: Overview / Tasks / Routines / Home / Supplies / People / Homi & account
- priority: Normal / Important
- recent campaign status/history

A broad send always asks for a second Homi confirmation.

Client Firestore rules allow only an active developer-admin account to create a tightly validated queued campaign. The client cannot mark a campaign sent, edit delivery counts or grant developer access.

Cloud Functions re-check the developer-admin record before delivery.

### Test sends

**Just this account** reads the signed-in developer's enabled device records, applies that device's category preference and sends directly to the token(s). Direct send/failure counts are recorded.

### Broadcast sends

**All enabled Homi devices** uses Firebase Cloud Messaging topics:

- `homi_updates`
- `homi_service`
- `homi_security`

Only installations with the matching Homi category enabled subscribe to that topic. A broadcast campaign records that FCM accepted the broadcast and its FCM message ID; it does not pretend topic acceptance is a per-device read/delivery receipt.

## Foreground, background and tap routing

- FCM foreground messages are rendered through Homi's local notification channels so they remain visible while the app is open.
- Background/terminated FCM notification messages are displayed by Android/FCM.
- `getInitialMessage` and `onMessageOpenedApp` route remote-notification taps.
- local-notification launch details and notification-response callbacks route local-notification taps.
- supported destinations are Overview, Tasks, Routines, Home, Supplies, People and Homi & account.

## Android integration

Because the Android host is intentionally local/untracked, run:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\enable-notifications-android.ps1
```

The helper idempotently adds/verifies:

- Android 13+ `POST_NOTIFICATIONS`
- `RECEIVE_BOOT_COMPLETED`
- scheduled-notification receiver
- boot/package-replace rescheduling receiver
- the approved Homi monochrome notification icon as `drawable/homi_notification.png`
- multidex
- core library desugaring for scheduled local notifications

It does not modify Firebase keys, Maps keys, signing values or other secrets.

## Cloud deployment

The notification backend lives under `functions/` and uses Firebase Cloud Functions 2nd gen in `africa-south1`.

Deploy it together with Firestore rules using:

```bash
bash scripts/deploy-notification-backend.sh
```

The script verifies the permanent Homi project number before deployment, installs Functions dependencies, syntax-checks `functions/index.js`, and deploys Firestore + Functions to `homi-ee80a`.

## Developer-admin provisioning

Obtain the intended developer Firebase Auth UID directly from **Firebase Console → Authentication → Users**. Do not send or commit it.

In Cloud Shell:

```bash
bash scripts/manage-developer-admin.sh '<FIREBASE_AUTH_UID>' enable
```

Use `disable` to revoke access. The script guards both project ID and project number before changing the server-only admin record.

## App Check

The development debug token has been registered. App Check enforcement remains off until valid debug and release traffic is confirmed. Enabling App Check enforcement is a separate release-hardening decision and must not be confused with notification permission.

## Privacy / safety boundary

Notification payloads should minimise sensitive content.

- no coordinates or precise addresses in developer broadcasts;
- no household Task title in server-generated lock-screen Task notifications;
- People hearts disclose the sender name because that is the purpose of the check-in;
- location sharing remains independently controlled and a heart never enables it;
- notifications are not emergency delivery and Homi does not guarantee a message was seen;
- notification tokens are delivery identifiers and are deleted/disabled through sign-out/account lifecycle controls described above.
