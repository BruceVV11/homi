# Homi 0.9.1+12 — restore People map and refine check-ins

Date: 2026-09-10
Status: source implementation pending Flutter validation and device acceptance

## Why this refinement exists

The first 0.9.0 device review showed that the new lightweight People hub unnecessarily displaced an already-approved People experience. The existing map-first People page, persistent Homi shell/header and direct location controls were the approved product foundation and did not need to be replaced.

0.9.1 restores that foundation and treats the 0.9 safety/check-in additions as extensions of the existing People page rather than a redesign of it.

## People destination restored

The primary People tab again opens the established `PeoplePage` directly inside the normal Homi shell.

Preserved at the top of the page:

- existing People title/subtitle;
- embedded Google map immediately on entry;
- profile-photo map markers and person focus chips;
- Open map action;
- current-device location status;
- Live updates controls;
- existing location details and How Homi location works flow;
- persistent Homi top bar and bottom navigation supplied by the shell.

The temporary separate **Manage connections & live location** destination is no longer part of the primary flow. The old map, connection and live-location functionality remains directly available on People as before.

## Connections underneath the map

Accepted connections remain on the same People page and are now grouped underneath the existing map/location section:

- **Household** — people the user marked as Household;
- **Friends & trusted people** — accepted non-Household connections.

The existing Homi code, connect action, incoming/outgoing requests, per-person location share controls, profile pictures and relationship preferences are preserved.

Relationship editing is now exposed as an explicit labelled **Edit** action instead of relying on a small pencil icon as the main discovery cue.

## Safety & check-ins placement

**Safety & check-ins** remains accessible from People, but its entry is placed after the connection groups so it does not displace the map/location experience.

The emergency call shortcuts remain:

- `112` — mobile emergency;
- `10111` — police emergency;
- `10177` — ambulance emergency.

No direct-call permission or silent calling was introduced.

## Arrival check-in control language

The check-in enable/disable experience now deliberately follows the existing Notifications settings language:

- a status hero card explains the current state;
- when disabled, a full-width **Enable arrival check-ins** button is shown;
- when enabled, a settings-style row with an on/off switch is shown;
- Android background-location permission is handled through the established Homi confirmation/settings flow;
- after returning from Android Settings, Homi retries enabling rather than leaving the user with a button that appears to have done nothing.

If Home/Work or recipients have not been configured, the user receives a direct setup message instead of an unexplained no-op.

## Home and Work addresses

Home and Work can now be configured in either of two ways:

1. **Enter address** — the user types a street address/place; Homi resolves it through the existing device geocoding layer to latitude/longitude and a readable address.
2. **Set from here** — Homi captures the current device location locally and reverse-resolves it into a readable address when available.

The saved place model now includes an optional readable `address` alongside latitude/longitude. Older 0.9 saved place records without an address remain valid and load normally.

The address and coordinates remain user-scoped local data. The existing `sendArrivalCheckIn` backend still receives only `home`/`work` and selected trusted-recipient UIDs. Therefore **no backend schema or callable redeployment is required for 0.9.1**.

## Help-content cleanup

Large explanatory/help containers were removed from the check-in flow where they were not required for state or error feedback.

Arrival education now uses the same **How it works** pattern already established on Overview/Tasks: a small text action opens a focused Homi bottom sheet with concise explanation and a Got it action.

The check-in status hero is retained because it is a functional state control equivalent to the Notifications page, not a passive help box.

## Tests

The arrival persistence test now verifies:

- readable address survives local serialization;
- recipients/radius/cooldown continue to persist;
- legacy saved check-in JSON without an address remains readable.

No Firebase deployment is required after this client-only refinement unless a later source change modifies Functions, Firestore rules/indexes or another backend runtime surface.

- People opens map-first with normal Homi top/bottom navigation;
- connection groups appear below the map/location section;

- Safety & check-ins is lower on People;
