# Homi 0.13.3 (Build 21)

## Scope

Focused notification reliability follow-up after Build 20 device diagnostics.

### Confirmed diagnosis
- Firebase Cloud Messaging accepted direct delivery to the current Homi device.
- Android notification permission was granted.
- Android recorded the direct FCM notification.
- None of Homi's five custom Android notification channels existed after a clean app start.
- The Homi notification drawable existed in the local Android project.
- Release resource shrinking can remove notification drawables unless they are explicitly preserved; flutter_local_notifications documents this as a release-build requirement.

### Fixes
- Hydrates locally cached Homi notification preferences and last-known Android permission state before presenting notification settings.
- Prevents the Notifications page from briefly presenting an uninitialised state as notifications being off.
- Creates all Homi Android notification channels before icon-dependent flutter_local_notifications initialisation, then reconciles them again after initialisation.
- Reports notification-initialisation failures to Flutter diagnostics instead of silently swallowing them.
- Adds a repeatable Android release preparation script that:
  - preserves `@drawable/homi_notification` from resource shrinking;
  - verifies the local notification icon exists;
  - adds Firebase's default notification icon metadata if absent.
- Keeps the existing user-facing Notifications screen free of transport/diagnostic status cards.

## Required Android host preparation

Because Homi's Android host directory is intentionally local/untracked, run this from the repository before the release build:

```powershell
powershell -ExecutionPolicy Bypass -File .\tool\prepare_android_notification_release.ps1
```

The script is idempotent and must complete successfully before producing the release AAB.
