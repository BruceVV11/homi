## Overview — three most important Supplies

The old generic `X supplies need attention` card has been replaced with an actionable preview.

`SupplyAttention` ranks Supply problems:

1. Need to buy / zero tracked amount;
2. Expired;
3. Use soon;
4. Running low.

Overview now shows:

- the total attention count;
- up to the three highest-priority item names;
- each item's concise status;
- `+ N more need attention` when the list is longer;
- one tap still opens Supplies.

This makes the first screen useful even when a household has a long Supply list.

## Supplies — status sections

Supplies are now visually grouped into:

1. **Need to buy**
2. **Use soon**
3. **Running low**
4. **In stock**

Each section shows a count and short explanation. The existing status line remains visible on every Supply card as requested.

All existing 0.7 Supply behaviour remains:

- optional quantity tracking;
- quick-add defaults;
- +/- amount changes;
- direct amount/unit update;
- status-only mode;
- expiry dates;
- persisted custom icon;
- zero amount derives Need to buy.

## People — heart check-ins

The full People map now supports a deliberately small interaction with a trusted person.

When another person is selected, a heart button appears alongside Details.

Sending a heart:

- requires sign-in;
- requires an accepted trusted connection;
- does not alter household scope;
- does not alter location sharing;
- does not create a chat/message history;
- uses a server-side one-minute sender→recipient cooldown;
- sends the recipient **“{sender} is thinking about you!”**;
- opens People when the notification is tapped.

This gives Homi a lightweight human interaction without turning People into a messaging app.

## Complete notification system

0.8 adds notification handling across local household state, cloud relationship events and developer broadcasts.

### User notification settings

New path:

**Profile avatar → Homi & account → Notifications**

The normal notification permission is user initiated rather than requested on first launch.

Categories:

- Household attention
- Tasks & routines
- People
- Homi updates
- Service & security

The master switch applies to the current installation. Category preferences are local and are also mirrored into signed-in device records for direct backend delivery.

### Local notifications

`HomiNotificationService` schedules/reconciles:

- one-off Task due times;
- next Routine due time;
- Supply expiry warning three days before at 09:00 when schedulable;
- Supply expiry date at 09:00;
- Home service warning seven days before at 09:00 when schedulable;
- Home service due date at 09:00.

It also checks current household state so enabling notifications or opening the app while an item is already inside a warning window still has useful behaviour.

Newly critical states are grouped into **one household-attention notification**, with up to three reasons plus a remaining count. Active condition keys are persisted so Homi does not repeatedly notify about the same unchanged issue.

Examples include:

- Bread needs to be bought;
- Milk expires soon;
- yoghurt is expired;
- geyser service is due/coming up.

When the underlying condition resolves, its de-duplication key disappears, so a later genuine recurrence can notify again.

Scheduled reminders use Android `inexactAllowWhileIdle`; Homi does not request exact-alarm permission.

### Remote notification routing

FCM is integrated from startup:

- background handler registered after Firebase initialization;
- foreground FCM messages rendered through Homi local channels;
- background/terminated notification messages use FCM/Android presentation;
- `getInitialMessage` + `onMessageOpenedApp` handle remote-notification taps;
- local-notification launch/response callbacks handle local taps;
- all notification taps route into the intended Homi destination.

Supported destinations:

- Overview
- Tasks
- Routines
- Home
- Supplies
- People
- Homi & account

### Signed-in device registration

When notifications are enabled, a signed-in device stores its current FCM token and category preferences under:

`users/{uid}/devices/{deviceId}`

The Homi `deviceId` is a random installation ID, not a hardware or advertising ID.

Token refresh updates Firestore. Sign-out removes the signed-in user's push token before the Firebase Auth session ends. Invalid/unregistered tokens discovered during direct server delivery are automatically disabled.

## Trusted-person / household push events

New Cloud Functions in `africa-south1` handle:

- new Homi connection request → recipient;
- connection accepted → original sender;
- People heart → recipient;
- shared Task created/assigned → assignee or household viewers;
- shared Task completed by another member → Task creator.

Shared Task lock-screen messages deliberately do **not** include the Task title. The notification tells the recipient there is household activity, then the authenticated Tasks screen shows the actual household content.

## Developer notification centre

0.8 adds an admin-only notification composer inside Homi.

Developer access is provisioned outside the app through `developerAdmins/{uid}`. A normal user cannot self-grant this role through Firestore rules or the UI.

An authorised developer sees:

**Profile avatar → Homi & account → Developer notifications**

Controls:

- title, max 80 characters;
- message, max 280 characters;
- type: Homi update / Service or maintenance / Security;
- audience: own account test / all opted-in Homi installations;
- destination to open when tapped;
- normal / important priority;
- recent send history/status.

Broad sends require a second branded confirmation.

### Developer self-test

A test send targets only the developer's enabled signed-in device records and records direct FCM success/failure counts.

### Broadcast

Broad developer sends use opt-in FCM topics:

- `homi_updates`
- `homi_service`
- `homi_security`

This means local-only Homi users can still opt into product/service notices without creating an account.

The client subscribes/unsubscribes the installation as the user changes those categories. A broadcast campaign records whether FCM accepted the topic message and its FCM message ID. It does not present topic acceptance as a per-device read receipt.

## Cloud security

Firestore rules now add:

### `developerAdmins/{uid}`

- user may only `get` their own record;
- no client list/create/update/delete;
- developer access is provisioned externally.

### `notificationCampaigns/{id}`

- only active developer admin may read/create;
- create payload strictly validates creator UID, queued status, title/body lengths, allowed category, destination, audience and priority;
- client cannot edit send state or delete campaign records;
- Cloud Functions Admin SDK re-validates developer access before sending.

### `heartCooldowns/{sender_recipient}`

- completely server-only through client rules.

Existing restrictive user/connection/task/location rules remain in place.

## Account deletion and notification data

Account lifecycle was extended for notifications:

- sign-out removes the direct account-specific push token from the current user/device record;
- account deletion removes device registration before cloud/Auth cleanup;
- `AccountDataService` deletes the user/device collection as before;
- when the Homi `users/{uid}` document is deleted, a server function cleans inaccessible notification metadata:
  - heart cooldowns involving the UID;
  - `developerAdmins/{uid}`;
  - notification campaigns created by that UID.

Developer broadcast topic membership is installation preference state rather than account-owned Firestore data.

## Android host integration

Because `android/` is intentionally local/untracked, new helper:

`scripts/enable-notifications-android.ps1`

It idempotently adds/verifies:

- `POST_NOTIFICATIONS`;
- `RECEIVE_BOOT_COMPLETED`;
- local scheduled-notification receiver;
- boot/package-update rescheduling receiver;
- approved Homi monochrome status icon at `drawable/homi_notification.png`;
- multidex;
- core-library desugaring (`desugar_jdk_libs:2.1.4`).

It does not print/change Firebase, Maps, signing or secret values.

## Backend deployment / developer access helpers

### Deploy notifications

`scripts/deploy-notification-backend.sh`

- locks project to `homi-ee80a` and project number `883068189841`;
- installs Cloud Functions packages;
- syntax-checks `functions/index.js`;
- deploys Firestore + Functions.

`scripts/manage-developer-admin.sh <firebase-auth-uid> <enable|disable>`

The Firebase Auth UID is obtained privately from Firebase Console and entered directly into Cloud Shell. It should not be pasted into chat or committed.
