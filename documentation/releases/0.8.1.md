# Homi 0.8.1 — Release hardening

Version: `0.8.1+9`

## Purpose

This pass hardens the already-working 0.8 notification/location collaboration layer before store release. It is intentionally focused on abuse resistance, cost containment, stricter Firestore validation and notification restraint rather than adding another large product surface.

## Confirmed 0.8 device state

Bruce confirmed on the Samsung S25 Ultra that normal local notifications and developer self-test notifications are delivering correctly. The Developer notifications centre is active for the intended account.

The broad **All enabled Homi devices** path is implemented through FCM topics. It was deliberately not used during the first notification proof so an unverified test could not accidentally reach every opted-in installation. The self-test proves the campaign trigger/backend path; the topic branch should still receive one controlled pre-release test before public users exist.

## Notification restraint

- Fresh/default Homi preferences now keep **Homi updates** off until the user explicitly enables that category.
- Unknown remote notification categories fail closed instead of being delivered by default.
- Direct notification fan-out reads at most 12 registered devices for one account. This bounds database reads and FCM fan-out if a user/device registration is ever polluted.
- Existing Household attention, Tasks & routines, People and Service & security controls remain separate.

## Callable Function protection

`sendHeart` now requires a valid Firebase App Check token in addition to Firebase Authentication and an accepted trusted connection.

Server limits now include:

- one-minute sender→recipient heart cooldown;
- 40 successful heart attempts per sender fixed 24-hour window;
- maximum 3 concurrent `sendHeart` instances;
- global Cloud Functions maximum reduced from 10 to 5 instances.

This does not replace platform quotas/budgets, but it materially reduces runaway scaling and simple scripted abuse.

## Event notification abuse limits

Server-only fixed-window counters suppress excessive push generation while keeping the underlying product record intact:

- connection-request pushes: 20/hour per initiator;
- shared-task creation pushes: 60/hour per creator;
- shared-task completion pushes: 120/hour per completing user;
- developer self-test campaigns: 30/hour;
- developer broad campaigns: 6/hour and 20/24 hours.

These counters are stored in `serverRateLimits`, which is completely inaccessible to mobile clients and is cleaned during Homi account deletion.

## Firestore hardening

The rules now validate substantially more than identity alone.

### Device registrations

- bounded document ID length;
- allowed field set only;
- push token length bounded;
- notification preferences must be booleans.

### Developer campaigns

- only an active server-provisioned developer can create a campaign;
- exact client field allow-list;
- bounded title/body;
- bounded category/route/audience/priority values;
- server timestamp required;
- clients cannot update delivery status.

### Homi codes

- exact lookup only, never listable;
- six-character IDs;
- compact owner-only schema;
- bounded display name/photo URL;
- server timestamp required.

### Connections

- exact field allow-list;
- two-member participant structure;
- document ID tied to `aUid_bUid`;
- bounded identity strings;
- only invited recipient can transition pending → accepted;
- acceptance may change only status/acceptedAt/updatedAt.

### People preferences

- only accepted connections can receive a relationship/scope preference;
- exact field allow-list;
- relationship length bounded;
- scope is only `household` or `friend`.

### Shared Tasks

- exact field allow-list and text-size limits;
- completion starts empty;
- a completing member can only write completion-related fields;
- `completedByUid` must equal the authenticated user when marking complete;
- completion cannot spoof another person;
- non-creators cannot arbitrarily delete an active shared Task; cleanup is allowed after its purge time.

The current multi-member shared-task create model still relies on the creator-provided member list. Full Household identity/sync should replace this with a server-derived Household membership model before Homi claims complete shared-household state.

### Location

Latest location writes are now schema constrained:

- only expected fields;
- latitude/longitude bounds;
- non-negative bounded accuracy;
- battery 0–100;
- boolean charging state;
- server timestamp required;
- source limited to Homi's known foreground/background capture modes.

Location-share records are similarly limited to owner/viewer/active/updatedAt and still require an accepted trusted connection.

## Cost-security layers still required before public release

Code-level limits are only one layer. Before public release:

1. verify valid App Check metrics from the registered debug build;
2. configure Play Integrity for the Play-signed release build;
3. enable App Check enforcement for Cloud Firestore after legitimate debug/release traffic is proven;
4. keep App Check enforcement on callable Functions such as `sendHeart`;
5. migrate Cloud Functions from the broad Compute default runtime identity to the existing least-privilege `homi-backend-runtime@homi-ee80a.iam.gserviceaccount.com` identity after its Eventarc/Run permissions are proven;
6. use Google Cloud budget alerts and, if available/appropriate for the account, project/service spend caps; ordinary budget alerts are not a hard spending cap;
7. keep function maximum-instance settings in source so deployments cannot silently remove them;
8. review Cloud Monitoring for unusual Firestore writes, Function invocations and FCM-trigger patterns during testing.

## Product release blockers still outside this pass

Homi is close visually, but public release still requires the product and store work tracked in `documentation/RELEASE_READINESS.md`, especially full Household cloud-sync semantics if multi-person shared Home/Routine/Supply state is part of the launch promise, production signing/OAuth/App Check fingerprints, Play background-location declaration, external account-deletion URL, public Privacy/Terms pages and final store/Data Safety materials.
