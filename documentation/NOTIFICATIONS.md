# Homi Notifications

Date: 2026-09-10
Source version: `0.9.0+11`

## Product principle

Homi notifications exist to reduce uncertainty, not create another stream of noise.

The notification system separates:

1. household attention generated from data on the current device;
2. shared household / trusted-person events generated by Homi's cloud backend;
3. arrival check-ins generated by an explicitly enabled local Home/Work transition and delivered through Homi's protected backend;
4. developer product, service and security notices;
5. the always-visible Android foreground-service notification used while live location/check-ins are active.

The foreground location notification is operational Android disclosure and is not controlled by the optional notification categories below.

## Fresh-install permission and defaults

Homi `0.9.0+11` defaults useful operational notifications **on** for a fresh installation:

- master operational notifications: ON;
- Household attention: ON;
- Tasks & routines: ON;
- People: ON;
- Service & security: ON;
- Homi updates/product announcements: OFF.

Homi Updates remains separately opt-in because product announcements are not required for household/safety operation.

Android still owns the actual runtime notification permission. On a fresh install Homi asks for that system permission once. If the user denies or dismisses the request, Homi does not repeatedly interrupt them on every launch. They can retry from:

**Profile avatar → Homi & account → Notifications**

or Android Settings.

Existing persisted notification preferences remain authoritative. An existing user who deliberately turned Homi notifications off is not silently opted back in by the new fresh-install default.

## Device-level categories

The device-level Homi settings are:

- Household attention;
- Tasks & routines;
- People;
- Homi updates;
- Service & security.

The master switch applies only to this installation. Category choices are stored locally and, for a signed-in device, mirrored through its server-protected FCM device registration so the backend can avoid direct messages the installation has disabled.

Unknown remote categories fail closed rather than silently notifying.

Developer broadcast categories use FCM topic subscriptions so a local-only installation can receive enabled Homi product/service notices without creating an account. Topic subscriptions are updated when the user changes the relevant category.

## Local household notifications

Local household reminders use `flutter_local_notifications` and are rebuilt from local Homi state whenever the user changes Tasks, Routines, Supplies or Home records.

Current behaviour:

| Event | Timing | Category | Destination |
| --- | --- | --- | --- |
| One-off Task with due time | saved due date/time | Tasks & routines | Tasks |
| Recurring Routine | next due date/time | Tasks & routines | Routines |
| Supply expiry warning | 3 days before at 09:00 when schedulable | Household attention | Supplies |
| Supply expiry date | expiry date at 09:00 | Household attention | Supplies |
| Home service warning | 7 days before at 09:00 when schedulable | Household attention | Home |
| Home service due | service date at 09:00 | Household attention | Home |
| Newly out-of-stock / Need to buy Supply | once when entering the critical state | Household attention | Supplies |

Scheduled local reminders use inexact Android scheduling rather than exact alarms. Homi therefore does not request exact-alarm permission. Android may defer an inexact reminder while conserving power.

Homi stores notification IDs for the schedules it owns, cancels/rebuilds only those IDs, and does not cancel unrelated Android notifications.

## Trusted-person notifications

Cloud Functions produce direct, preference-aware notifications for authenticated relationship/collaboration events.

### Connection request

The recipient receives a Homi People notification when another user sends a connection request. Excessive notification generation from one initiator is server-limited.

### Connection accepted

The original sender receives a People notification when the invited user accepts.

### Hearts

The full People map exposes a deliberately small heart action for a selected trusted person:

- authenticated sender required;
- Firebase App Check required;
- accepted trusted connection required;
- one-minute sender→recipient cooldown;
- 40 hearts per sender per fixed 24-hour window;
- recipient sees **“{name} is thinking about you!”** when People notifications are enabled;
- tapping opens People.

A heart never enables or changes location sharing and is not proof that the recipient saw it.

### Shared Tasks

When a shared Task is created, the selected assignee is notified, or household-visible members are notified when the Task is for Anyone at home.

When somebody other than the Task creator completes it, the creator receives a completion notification.

Lock-screen notification bodies intentionally avoid reproducing the Task title. The user opens authenticated Homi Tasks to read household content.

### Arrival check-ins

`sendArrivalCheckIn` delivers Home/Work arrival notifications through the People category.

The local device detects the outside → inside transition. The backend then:

- requires Firebase Authentication and App Check;
- requires verified email for password-provider accounts;
- accepts only Home/Work labels;
- accepts at most 10 selected recipients;
- verifies every recipient is an accepted trusted Homi connection;
- applies sender rate limits of 20/hour and 60/day;
- reads no more than 12 push-enabled device records per recipient;
- respects each recipient device's People preference;
- sends only the sender name and Home/Work label, not saved coordinates or addresses.

Example notification title:

**“Sam arrived home”**

The body remains concise and does not expose precise location.

Arrival notification delivery is not guaranteed emergency communication. Connectivity, Android power management, notification permission and FCM delivery can delay or suppress a message.

## Noise and abuse control

Current controls include:

- category-level switches;
- Homi updates separately opt-in;
- expiry/maintenance reminders scheduled for 09:00 rather than overnight;
- critical Supply changes de-duplicated while the item remains in that state;
- only the nearest 60 local schedules retained after chronological sorting;
- broad developer notices limited to product/service/security categories;
- People heart one-minute pair cooldown and 40/day sender cap;
- arrival check-in one-hour local per-place cooldown plus 20/hour and 60/day server caps;
- connection-request generation capped at 20/hour per initiator;
- shared Task creation generation capped at 60/hour per creator;
- shared Task completion generation capped at 120/hour per completing user;
- developer self-tests capped at 30/hour;
- developer broad campaigns capped at 6/hour and 20/24h;
- direct notification fan-out capped at 12 enabled device registrations per account;
- bounded Cloud Function instance counts;
- no precise coordinates or addresses in People/check-in lock-screen payloads.

Server counters live under `serverRateLimits` and are inaccessible to mobile clients. These limits complement Firebase App Check, IAM, monitoring and Cloud Billing controls.

## FCM device registration

When notifications are enabled and a user is signed in, Homi stores the current FCM registration under:

`users/{uid}/devices/{deviceId}`

The document contains the push token, platform, master notification state, category preferences and server update timestamp.

Device registration/removal is server-controlled through App-Check-protected callable Functions. The device ID is a random installation identifier stored in Homi local preferences; it is not a hardware serial or advertising identifier.

Signing out removes the push registration from the signed-in user before ending Firebase Auth. Account deletion removes Homi-managed device registrations through the account lifecycle pipeline. Invalid/unregistered FCM tokens discovered during server delivery are disabled automatically.

## Developer notification control

Developer notification access remains server-provisioned through `developerAdmins/{uid}` and cannot be self-granted by the mobile app.

The composer supports:

- title (maximum 80 characters);
- message (maximum 280 characters);
- type: Homi update / Service or maintenance / Security;
- audience: current developer account test / all enabled Homi installations;
- deep-link destination;
- delivery urgency;
- recent campaign status/history.

Homi Update campaigns always use Normal delivery. Service/Security notices may request Important only when appropriate.

Bruce has previously proven developer self-test delivery on the Samsung S25 Ultra. A controlled **All enabled Homi devices** broadcast remains a device/release regression gate.

## Foreground, background and tap routing

- FCM foreground messages are rendered through Homi local channels so they remain visible while Homi is open.
- Background/terminated FCM notification messages are displayed by Android/FCM.
- remote/local notification taps route to supported destinations including People.
- arrival check-ins use the existing People route/category.

## Android integration

Because the Android host is intentionally local/untracked, the existing helper remains the source of truth for notification host configuration:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\enable-notifications-android.ps1
```

It idempotently adds/verifies Android notification permission, boot rescheduling integration, the Homi notification icon, multidex and desugaring without modifying Firebase/Maps/signing secrets.

## Cloud deployment

The notification/check-in backend lives under `functions/` and runs in `africa-south1` using:

`homi-backend-runtime@homi-ee80a.iam.gserviceaccount.com`

Deploy through:

```bash
bash scripts/deploy-notification-backend.sh
```

The helper now:

1. validates Node 22 and the exact Homi project identity;
2. prepares a disposable synchronized Functions lock;
3. validates dependencies through local `npm ci`;
4. syntax-checks all Function modules including `check_in.js`;
5. runs the mandatory Firestore Emulator security suite;
6. deploys Firestore separately;
7. deploys discovered Function exports in batches of five.

The `0.8.2+10` backend deployment using this corrected batched path has been confirmed successful. The new 0.9 arrival callable still requires its own deployment/verification after the 0.9 Flutter source passes local analysis/tests.

## Privacy / safety boundary

Notification payloads minimise sensitive content.

- no coordinates or precise saved-place addresses in arrival check-ins;
- no household Task title in server-generated lock-screen Task notifications;
- People hearts disclose the sender name because that is their purpose;
- arrival check-ins disclose sender name plus Home/Work because that is their explicit purpose;
- notifications never enable location sharing;
- notifications are not emergency delivery and Homi does not guarantee a message was seen;
- emergency-service call shortcuts are separate from Homi notifications and do not send an automatic alert to trusted people or responders.
