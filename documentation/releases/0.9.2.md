# Homi 0.9.2+13 — People, map safety and Google Places corrective pass

Date: 2026-09-11
Status: implemented in source; Flutter/backend/device validation pending

## Why this pass exists

The first 0.9 device review showed that several People/Safety additions were functionally useful but still did not fit the approved Homi interaction model closely enough. The same device pass also exposed a raw `UNAUTHENTICATED` People error while Android logs contained Firestore reachability/name-resolution failures.

0.9.2 is a corrective pass. It keeps the restored map-first People page and fixes the affected interaction, authentication-recovery and saved-place contracts without redesigning the primary shell.

## Safety & check-ins UI

- Removed the large green Arrival check-ins status/help hero.
- Removed the redundant success notice that only repeated that check-ins were on.
- Arrival check-ins now use one Notifications-style settings card at all times.
- Its switch directly reflects the real saved enabled state.
- Its copy explains what the switch does and that turning it off keeps Home/Work settings.
- `How it works` now includes the same information icon language used by other Homi contextual-help actions.
- Success operations stay quiet; inline notices are reserved for actionable errors or missing setup.

## Google Places address selection

Homi now uses `flutter_google_places_sdk` against **Places API (New)** for Home/Work address selection.

- Autocomplete is restricted to South African results.
- Suggestions come from Google Places rather than accepting an unverified free-text coordinate lookup as the primary path.
- Selecting a suggestion fetches only the Place ID, formatted address and coordinates needed by Homi.
- Google's required attribution asset is displayed with autocomplete results.
- `Set from here` remains available and reverse-resolves the phone's current location.
- The Places key is never committed to source. Development builds receive the existing Android-restricted Homi Places key through `--dart-define=HOMI_PLACES_API_KEY=...`.

The existing `homi-ee80a` cloud setup already enables Places API (New) and the existing Android key creation helper restricts the credential to Homi's package/SHA plus Maps SDK for Android and Places API (New).

## Arrival recipients

Saved-place cards no longer summarize a recipient as text such as `notifies Casey`.

Selected recipients are shown as profile-photo/initial avatars with their name beneath the image. The existing People selector remains the editing surface.

## Exact Home/Work visibility

Arrival notification delivery and exact-place visibility are intentionally separate permissions.

Each configured Home/Work card now has an explicit:

**Show this place to selected people**

switch.

The switch is off by default, including for migrated 0.9/0.9.1 settings. When on:

1. the viewer must be one of that place's selected trusted people;
2. the viewer must still be an accepted Homi connection;
3. the owner must also currently have location sharing active to that viewer.

Only then can that viewer read the exact Home/Work address/coordinate in Person Details.

The owner always sees their own locally saved Home/Work in their own Person Details.

### Cloud representation

A minimal optional cloud copy lives at:

`sharedPlaces/{ownerUid}/places/{home|work}`

with:

- owner UID;
- place kind;
- latitude/longitude;
- readable address;
- explicitly selected viewer UIDs;
- server update timestamp.

Clients cannot create/update/delete these documents directly. `setSharedArrivalPlace` is the protected server mutation path. Firestore rules independently gate reads by viewer selection + accepted connection + active owner→viewer location share.

Removing a connection strips stale saved-place viewer access. Account deletion removes owned shared-place documents. Turning the per-place switch off removes the cloud copy while preserving the owner's local arrival settings.

The `sendArrivalCheckIn` callable remains unchanged: arrival push delivery still receives no saved coordinate or address.

## Full People map

The approved full-screen map remains the main location surface and now has emergency actions in the lower thumb-reach control area:

- **SOS · 112** — one tap opens the phone application with 112 ready;
- **Emergency numbers** — opens 112, 10111 and 10177 choices without first leaving the map.

Homi still does not request silent direct-call permission, dispatch responders or automatically transmit location to emergency services.

Person Details on the full map now includes:

- latest shared/current location entry;
- Home;
- Work.

For the current user, Home/Work comes from local arrival settings. For another person, Home/Work appears only through the explicit privacy boundary above.

## People authentication/reachability recovery

Two client issues were hardened:

1. `PeopleHubPage` now re-keys the preserved map-first `PeoplePage` when Firebase's authenticated UID changes/restores, so kept-alive realtime subscriptions cannot remain attached to an old signed-out identity.
2. `HomiCloudActions` now maps protected callable failures to product language and, for one `unauthenticated` failure, refreshes the Firebase ID token and App Check token then retries once.

Raw backend codes such as `UNAUTHENTICATED` must not be surfaced as Homi UI copy.

The supplied Android logcat from the failing device session also contained Firestore `UNAVAILABLE`/DNS name-resolution messages. Firestore listeners are expected to recover when connectivity/DNS recovers; Homi retains the last valid People state and uses user-facing retry/reachability wording rather than exposing transport codes.

## Backend additions

New backend module: `functions/saved_places.js`.

New exports:

- `setSharedArrivalPlace`
- `onHomiUserSharedPlacesDeleted`

`setSharedArrivalPlace`:

- requires Firebase Authentication;
- requires App Check;
- requires verified email for password-provider sharing;
- accepts only Home/Work;
- bounds coordinates/address/viewer count;
- revalidates accepted trusted connections;
- applies server-side hourly/daily rate limits;
- never accepts an arbitrary unconnected viewer.

`onTrustedConnectionDeleted` now removes the disconnected UID from any shared Home/Work viewer list so reconnecting later cannot revive stale access.

## Firestore rules/security gate

A new `sharedPlaces` rule permits exact document reads only to:

- the owner; or
- an explicitly listed viewer who still has an accepted connection and active location share from the owner.

All client mutation remains denied.

The Firestore emulator suite now includes this privacy boundary. The expanded suite must pass before 0.9.2 backend deployment.

## Migration/data compatibility

Existing 0.9/0.9.1 local arrival settings remain readable.

New fields default safely:

- `placeId`: null;
- `shareAddressWithRecipients`: false.

Existing arrival recipients therefore do **not** gain exact Home/Work visibility after updating.

## Deployment state

This pass changes Flutter source **and** backend/rules, unlike 0.9.1.

Required gates in order:

1. `flutter pub get`
2. `flutter analyze`
3. `flutter test`
4. governed backend deployment helper, including expanded Firestore emulator gate
5. configure the private local Places key for the debug run without committing/pasting it
6. Samsung S25 Ultra acceptance
7. second-account/device verification of exact-place visibility and arrival delivery

Do not claim 0.9.2 compiled, backend-deployed or device-accepted until those real gates are completed.
