## Why the broad deploy was a poor fit

0.8.2 expanded Homi from a comparatively small notification backend into a much broader Gen-2 Functions security/collaboration backend. The helper was still issuing one broad Functions deployment, causing Firebase to attempt roughly twenty Function updates in one burst.

Firebase currently recommends deploying named Functions when a project contains more than five Functions and, for larger sets, using groups of ten or fewer to avoid deployment quota/control-plane failures. The observed pattern is consistent with that class of provider-side deployment pressure, although the CLI did not print a specific HTTP status code in this run.

## Source repair

`scripts/deploy-notification-backend.sh` now:

- verifies local Node major version 22 before backend validation/deploy;
- keeps the synchronized disposable Functions lockfile flow;
- keeps the mandatory 12/12 Firestore security gate;
- keeps the safe one-time stale-trigger migration, which now automatically skips because the migration has completed;
- deploys Firestore rules/indexes as their own surface;
- derives the current Homi Function export names from `functions/entrypoint.js` rather than maintaining a duplicated hard-coded list;
- deploys Functions in deterministic batches of **5**;
- stops immediately on a failed batch;
- allows already-successful/unchanged Functions to be skipped naturally on a later run.

This returns the Homi backend release path to a smaller, resumable deployment shape instead of one large concurrent Functions burst.
