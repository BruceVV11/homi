# Homi 0.8.2+10 — security closure and protected collaboration

## Scope

0.8.2 is a security-focused pre-release pass. It preserves the approved 0.8 product/UI while moving sensitive collaboration mutations behind App-Check-protected Cloud Functions, tightening Firestore to read-mostly client access, hardening Authentication defaults and closing stale-access/cost-abuse paths found during the pre-release review.

## Sensitive writes moved server-side

The Flutter client now uses `HomiCloudActions` for:

- Homi identity/code issuance;
- exact Homi-code lookup and connection creation;
- connection acceptance/removal;
- trusted-person relationship/scope changes;
- per-person location sharing authorization;
- shared Task create/toggle/remove;
- developer notification campaign queueing;
- cloud account-data deletion.

All of these callables enforce Firebase App Check. Sharing callables also require a verified email when the account uses the password provider.

## Firestore client boundary

Direct client mutation is now denied for:

- user identity/profile documents;
- Homi code directory;
- connections;
- trusted-person preferences;
- shared Tasks;
- location-share permissions;
- developer notification campaigns;
- developer-admin records;
- heart cooldowns and server rate-limit records.

Realtime reads remain available only where required by the product.

Latest location remains a direct device write because it is the high-frequency data path. It is owner-only, exact-schema validated and limited to one update of an existing document per 30 seconds. The app's normal live stream remains approximately two minutes/100 m and now avoids duplicate cloud writes inside that guard interval.

## Trusted People privacy fixes

- Homi codes are no longer client-readable/searchable.
- Code lookup is server-side, App-Check protected and limited to 30/hour and 100/day per account.
- Trusted connections are capped at 30/account.
- Connection documents are server-created using deterministic pair IDs.
- Removing a connection revokes bilateral share/preference state and detaches each person from shared Tasks derived from that relationship.
- Changing a person from Household to Friend/location-only removes them from Tasks created by that user, closing stale household-data visibility.
- A server deletion trigger provides the same cleanup as a backstop if a connection is removed administratively.

## Shared Task hardening

The app no longer supplies authoritative Task membership. The backend derives `memberUids` from accepted connections the creator has explicitly marked Household and verifies any assignee is one of those members.

Creator/completion identity comes from Firebase Authentication rather than client fields. Only the completer or Task creator can reopen a completed Task. Active removal remains creator-only; expired completed-history cleanup is authorized server-side.

## Authentication hardening

The create-account UI now requires 10–128 character passwords with uppercase, lowercase and numeric characters, disables credential autocorrect/suggestions and uses enumeration-safe reset feedback.

`scripts/configure-auth-security.sh` configures the server project for:

- improved email privacy / email enumeration protection;
- enforced new-password policy matching the app;
- no forced upgrade of existing test-account passwords on sign-in.

After reauthentication, Homi refreshes the Firebase ID token so the protected deletion backend receives the current `auth_time` claim.

## Account deletion

Cloud cleanup moved from cross-user Firestore client writes to the App-Check-protected `deleteHomiAccountData` callable. The backend requires recent authentication and is rate-limited. It removes Homi-managed cloud identity/collaboration data before the app deletes the Firebase Authentication identity and current-device local data.

## Developer notifications

Campaign creation now goes through an App-Check-protected developer callable; clients can no longer forge campaign documents directly.

The composer label is now **Delivery urgency**. Homi Update campaigns always use Normal delivery in both UI and backend. Service/Security notices may request Important delivery when genuinely time-sensitive.

## Functions cost/security controls

- global `maxInstances: 5`;
- global `minInstances: 0`;
- default memory `256MiB`;
- dedicated least-privilege runtime service account retained;
- individual high-risk callables use smaller instance caps;
- server fixed-window limits added to connection lookup/mutation, preferences, sharing, shared Tasks, developer queueing and account deletion;
- existing notification and Heart fan-out limits retained;
- maximum 12 push-enabled device records read per user for direct delivery.

## Cloud Shell hygiene

- Function dependency cache remains under a temporary workspace and generated `node_modules` is removed after deployment.
- Firestore security-test dependencies remain entirely in temporary storage.
- `scripts/cleanup-cloud-shell.sh` safely clears only generated Homi dependencies/caches/logs.
- Direct dependency versions for Functions and Firestore security tests are pinned to reduce release drift.

### 10 September 2026 dependency pin repair

The first 0.8.2 Cloud Shell deployment stopped correctly at `npm install` with `ERESOLVE`: the security pass had pinned `firebase-admin` to `14.1.0` and `firebase-functions` to `7.0.0`, but Functions 7.0.0 only declares Firebase Admin support through v13. Homi now keeps deterministic exact dependency pins while using `firebase-functions` `7.3.2`, whose peer range supports Firebase Admin 14.x. The deployment gate remains strict; do not bypass this failure with `--force` or `--legacy-peer-deps`.

### 10 September 2026 shared-Task query gate repair

The next deployment attempt reached the Firestore Emulator gate and passed 11/12 tests. The legitimate `memberUids array-contains currentUid` shared-Task query was denied because the rule required both list typing and membership, which Firestore could not prove from the query constraint. The rule now uses query-compatible list membership while retaining server-only Task mutations, member-only document reads and denial of unfiltered collection reads. The next emulator run passed all 12 tests.

### 10 September 2026 Cloud Build lockfile repair

After the 12/12 Firestore security gate passed, Firebase successfully compiled and released the 0.8.2 Firestore rules and uploaded the Functions source. Cloud Build then rejected every Functions create/update at `npm ci` because the Cloud Shell checkout contained an **untracked stale `functions/package-lock.json`**. That lock still resolved `firebase-admin` 14.3.0 and lacked a transitive dependency required by the newly pinned manifest, while `functions/package.json` now requires `firebase-admin` 14.1.0 and `firebase-functions` 7.3.2.

GitHub does not currently track `functions/package-lock.json`. The original smooth Homi backend helper used normal `npm install`, which updated/created the local lock before Firebase packaged the Functions directory. The later Cloud Shell storage repair added `--package-lock=false`; this kept the stale local lock untouched even though Firebase still included that untracked file in its upload.

The deploy helper now restores the useful old behaviour without restoring the storage problem:

- any untracked stale Functions lock is removed before dependency preparation;
- a fresh lock matching `functions/package.json` is generated with `npm install --package-lock-only` using the temporary npm cache;
- local dependencies are then installed through `npm ci`, matching the Cloud Build install mode before any deployment is attempted;
- the generated lock remains present while Firebase packages/uploads the Functions source;
- untracked lock, generated `node_modules` and temporary npm cache are removed automatically when the helper exits.

This failure created a **partial backend deployment**: Firestore rules are already live because their release completed before the Function builds failed. Firebase reported failures for all targeted Function creates/updates, so the 0.8.2 Functions deployment remains pending retry. Existing previously deployed Functions were not intentionally deleted; Firebase explicitly skipped deletes after the failed Function deployment.

## Location notification refinement

The mandatory Android foreground-service notification now uses Homi's approved notification icon and a dedicated **Live location** channel with concise wording. It is explicitly ongoing while sharing is active; wake/Wi-Fi locks remain disabled.

The notification cannot be removed while Homi relies on an Android foreground location service for background sharing.

## Automated security gate

The Firestore emulator suite was replaced with `server.boundary.test.js`, matching the new architecture. It verifies client reads that must remain available and rejects direct mutation of the server-authorized collections.

`deploy-notification-backend.sh` continues to block deployment when this suite fails. The latest Cloud Shell proof on 10 September 2026 passed **12/12** security tests before Firestore rules were released.
