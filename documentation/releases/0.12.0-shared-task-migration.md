# Homi 0.12.0 — canonical shared Task migration amendment

Date: 2026-09-12
Applies to: `0.12.0+16` on `homi-0.12-shared-data-plane`
Status: **source candidate; final exact-head app and governed backend validation pending**

This amendment records the privacy migration required to move pre-0.12 shared one-off Tasks away from the older editable People preference scope and onto canonical Shared Household authorization.

## Why this migration exists

Pre-0.12 shared one-off Tasks used the older People preference scope. That scope could previously be set to Household independently of the canonical Household introduced in 0.11.

0.12 must therefore not keep trusting an old `memberUids` list by itself, and it must not silently widen an old Task to every newer canonical Household member.

## Current read boundary

The 0.12 client reads shared Tasks with both:

- `householdId == currentCanonicalHouseholdId`; and
- `memberUids array-contains currentUserUid`.

Firestore additionally requires that the caller still satisfies both halves of canonical Household membership: their membership pointer references that Household and the Household parent still contains their UID.

A composite Firestore index is source-controlled for this exact query.

Legacy Tasks with no safe canonical `householdId` fail closed under the new rule rather than remaining readable because of an obsolete People preference.

## Governed legacy migration

`functions/migrate_legacy_shared_tasks.js` is a deployment-time migration helper. It defaults to dry-run and never prints task text, names, UIDs or Household IDs.

For each pre-0.12 Task without `householdId`:

1. the creator must still have a valid canonical Household membership;
2. that creator must still appear in the canonical Household member list;
3. the new recipient list is the **intersection** of the Task's historical recipients and the current canonical Household, with the creator retained;
4. a historical assignee/completer outside that safe recipient set is detached;
5. the Task receives `householdId` and `audienceVersion: 0`.

This preserves eligible old Tasks without granting them to a newer Household member who was never part of the original audience.

Tasks that cannot be mapped safely remain stored but fail closed. They are not deleted merely to make the migration pass.

`--assert-stable` is a separate fail-closed mode. After an apply pass it refuses to continue if any safely migratable legacy Task still remains.

## Durable Household ownership of shared Tasks

Once a Task has a canonical `householdId`, the Household is the collaboration boundary; the Task does not become unusable merely because the account that originally created it later leaves.

Callable access still requires the acting user to be both:

- in the Task's stored safe `memberUids` audience; and
- a current canonical member of that exact `householdId`.

For new `audienceVersion: 1` Tasks, the current Household owner also has owner-level recovery permission to reopen/remove a Task when the original creator/completer is no longer available.

## New canonical Tasks versus migrated Tasks

New 0.12 Tasks are created with:

- canonical `householdId`;
- `audienceVersion: 1`;
- the current canonical Household `memberUids`.

`onHouseholdTaskMembershipChanged` updates **only** audience-version-1 Tasks when canonical membership changes. Removed assignees/completers are detached from stale UIDs.

Migrated pre-0.12 Tasks are `audienceVersion: 0` and are deliberately ignored by that audience synchronizer. A later Household join therefore cannot widen a historical Task beyond the recipient intersection established during migration.

## Governed deployment order

After Node 22 dependency install/lint, the five pure shared-Task policy tests, exact 37-export verification and the 23-test Firestore emulator gate pass, the backend helper proceeds in this order:

1. dry-run the legacy shared-Task migration to prove production read access and report counts;
2. reconcile the known legacy `onConnectionDeleted` Function, if it still exists, **before any new 0.12 Function deploy** so stale codebase drift cannot block later non-interactive deploys;
3. deploy only the canonical shared-Task callables plus `onHouseholdTaskMembershipChanged`;
4. prove those four Functions are ACTIVE;
5. apply the safe legacy Task migration;
6. run `--assert-stable` and stop if any safely migratable Task remains;
7. deploy the stricter Firestore rules/indexes;
8. continue the normal bounded Functions batches.

The process is idempotent and fail-closed. A failed migration or failed Function health check prevents the stricter rule deployment from continuing.

## Automated policy/security tests

`functions/household_task_policy.test.js` contains five pure Node tests covering:

1. migrated `audienceVersion: 0` Tasks are never widened;
2. canonical `audienceVersion: 1` Tasks follow current Household membership;
3. removed assignee/completion UIDs are stripped while valid attribution remains;
4. Household-owner reopen recovery is explicit;
5. creator/Household-owner active removal policy is explicit.

The governed Firestore suite contains **23 tests** for the final 0.12 candidate:

- 13 established server-boundary tests, with their shared-Task cases updated to the canonical 0.12 rule;
- 8 Household identity/data-plane tests;
- 2 dedicated canonical shared-Task query/fail-closed tests.

The security-test helper refuses to run if those three files do not declare exactly 23 tests, preventing an omitted suite from being mistaken for a passing gate.

The exact 5/5 policy and 23/23 Firestore results must still be proven by the governed Node 22 Cloud Shell run before 0.12 deployment.

## Remaining acceptance limitation

A second physical device is still unavailable. Emulator/security tests can prove authorization boundaries, but they do not justify claiming true two-device realtime UX acceptance. That remains explicitly pending.
