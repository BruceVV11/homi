# Homi 0.9.2+13 — People, map safety and Google Places corrective pass

Date: 2026-09-11
Status: Flutter static gate previously passed; backend deployed; Android Places client dependency migration pending Windows/device validation

## Why this pass exists

The first 0.9 device review showed that several People/Safety additions were useful but did not yet fit the approved Homi interaction model closely enough. The same device pass also exposed a raw `UNAUTHENTICATED` People error while Android logs contained Firestore reachability/name-resolution failures.

0.9.2 keeps the restored map-first People page and corrects the affected interaction, authentication-recovery and saved-place contracts without redesigning the primary shell.

## Safety & check-ins UI

- Removed the large green Arrival check-ins status/help hero.
- Removed the redundant success notice that only repeated that check-ins were on.
- Arrival check-ins use one Notifications-style settings card in both ON and OFF states.
- Its switch reflects the real persisted enabled state.
- Its copy explains what the switch does and that turning it off keeps Home/Work settings.
- `How it works` uses the information-icon language used by other Homi contextual-help actions.
- Success operations stay quiet; inline notices are reserved for actionable errors or missing setup.

## Google Places address selection

Home/Work supports Google Places API (New) autocomplete restricted to South Africa plus **Set from here**.

- Suggestions come from Google Places rather than accepting an unverified free-text coordinate lookup as the primary path.
- Selecting a suggestion fetches only the Place ID, formatted address and coordinates needed by Homi.
- Google attribution is displayed with autocomplete results.
- `Set from here` remains available and reverse-resolves the phone's current location.
- The Places key is never committed to source. Development runs receive the existing Android-restricted Homi Places key through `--dart-define=HOMI_PLACES_API_KEY=...`.

The existing `homi-ee80a` cloud setup enables Places API (New), Maps SDK for Android and API Keys API. The mobile credential remains package/SHA restricted rather than using an unrestricted browser/server key.

### Android dependency failure history and final migration

The first physical-device Gradle build resolved the original `flutter_google_places_sdk 0.4.3` stack to `flutter_google_places_sdk_android 0.2.2`. That Android package failed Kotlin compilation with unresolved Google Places properties including `address`, `latLng`, `name`, `nameLanguageCode`, `phoneNumber`, `userRatingsTotal` and `placeTypes`.

An initial corrective attempt pinned `flutter_google_places_sdk_android 0.2.3` because the upstream changelog advertised it as the replacement. Bruce's Windows resolver proved that `0.2.3` is not actually published to pub.dev:

`Because homi depends on flutter_google_places_sdk_android 0.2.3 which doesn't match any versions, version solving failed.`

That resolver failure happened before analysis, tests or an Android build and did not change the already deployed backend or the existing lock file. Upstream issue #136 independently confirms the advertised Android `0.2.3` artifact is unavailable, and issue #137 matches Homi's exact `0.2.2` Kotlin build failure.

Homi therefore no longer uses that abandoned dependency path. It now uses:

```yaml
google_places_sdk_plus: 1.1.0
```

`google_places_sdk_plus` is an independently maintained fork of the original plugin that keeps the native Android/iOS Places SDK model and supports Places API (New). Version 1.1.0 requires Dart >=3.11 and Flutter >=3.41, matching Homi's Dart 3.11.3 / Flutter 3.41.x toolchain. Its Android implementation is federated and currently has a compatible 1.1.x line; the exact resolved version must be recorded from Bruce's local `pubspec.lock`, not guessed in source.

Homi's wrapper was migrated to the fork's API:

- import changed to `package:google_places_sdk_plus/google_places_sdk_plus.dart`;
- Places client construction no longer uses the removed `useNewApi` switch because the fork is New-API-only;
- place detail fields use `PlaceField.Id`, `PlaceField.FormattedAddress` and `PlaceField.Location`;
- nullable autocomplete prediction fields are handled safely;
- Google attribution uses the fork's current asset constant.

This is a Flutter-client dependency migration only. No Functions, Firestore rules/indexes or backend contract changed, so **do not redeploy Firebase** for this correction.

## Arrival recipients

Saved-place cards show selected arrival recipients as profile-photo/initial avatars with the person's name beneath. The existing People selector remains the editing surface.

## Exact Home/Work visibility

Arrival notification delivery and exact-place visibility are intentionally separate permissions.

Each configured Home/Work card has an explicit **Show this place to selected people** switch, off by default. A different user may see an exact saved place only when all of these remain true:

1. the viewer is explicitly selected for that place;
2. the connection is still accepted;
3. the owner currently has location sharing active to that viewer.

The owner always sees their own local Home/Work in Person Details.

The optional cloud copy lives at:

`sharedPlaces/{ownerUid}/places/{home|work}`

and contains only owner UID, place kind, latitude/longitude, readable address, explicit viewer UIDs and server update timestamp. Clients cannot mutate these documents directly. `setSharedArrivalPlace` is the protected mutation path, and Firestore rules independently enforce the read boundary.

Removing a connection strips stale viewer access. Account deletion removes owned shared-place documents. Turning the per-place switch off removes the cloud copy while preserving the owner's local arrival setup.

`sendArrivalCheckIn` remains address/coordinate-free.

## Full People map

The approved full-screen map remains the primary location surface and now has emergency actions in the lower thumb-reach area:

- **SOS · 112** opens the phone application with 112 ready;
- **Emergency numbers** exposes 112, 10111 and 10177 without first leaving the map.

Homi does not request silent direct-call permission, dispatch responders or automatically transmit location to emergency services.

Person Details includes latest location plus Home and Work. Self Home/Work comes from local arrival settings; another person's Home/Work appears only through the exact-place privacy boundary above.

## People authentication/reachability recovery

- `PeopleHubPage` re-keys the preserved map-first `PeoplePage` when Firebase's authenticated UID changes/restores so kept-alive realtime subscriptions cannot remain attached to an old signed-out identity.
- `HomiCloudActions` maps protected callable failures to product language and, on one `unauthenticated` result, refreshes the Firebase ID token and App Check token and retries once.
- Raw backend codes such as `UNAUTHENTICATED` must not surface in Homi UI.
- Firestore `UNAVAILABLE`/DNS failures remain a separate transport condition; listeners retain/recover state and show product-level connection wording.

## Backend additions

0.9.2 added `functions/saved_places.js` with:

- `setSharedArrivalPlace`;
- `onHomiUserSharedPlacesDeleted`.

`setSharedArrivalPlace` requires Firebase Authentication + App Check, requires verified email for password-provider sharing, accepts only Home/Work, bounds coordinates/address/viewer count, revalidates accepted connections and applies server-side hourly/daily limits.

`onTrustedConnectionDeleted` also strips disconnected users from shared Home/Work viewer lists.

## Firestore rules/security gate

The `sharedPlaces` rule permits exact reads only to the owner or an explicitly selected viewer who still has an accepted connection and active owner→viewer location share. All client mutations remain denied.

The expanded Firestore emulator suite passed **13/13** before deployment.

## Migration/data compatibility

Existing 0.9/0.9.1 local arrival settings remain readable. New fields default safely:

- `placeId`: null;
- `shareAddressWithRecipients`: false.

Existing arrival recipients therefore do not gain exact Home/Work visibility merely by updating.
